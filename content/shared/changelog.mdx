# Changelog

What changed in each version of the specification, extensions, and guides, newest first. Each
published version stays at its own URL, such as [/docs/0.1/spec](/docs/0.1/spec).

## Draft 0.3 {#v0-3}

In progress, at [/docs/spec](/docs/spec). This list grows until 0.3 is published. Major changes are
design decisions. Minor changes fill gaps, make the text consistent, or follow an RFC. A change
tagged "Breaking" can require an implementation that followed the 0.2 text to change, whether it's
major or minor.

### Major changes {#v0-3-major}

<Change title="Sign-in types from the OAuth server metadata" breaking sections="3.1, 3.2, 4.4">

`auth.direct` and `auth.device` are removed from `poppy.json`. A Company offers Direct and Device
Sign-In when `grant_types_supported` in its OAuth server metadata includes `authorization_code` or
`urn:ietf:params:oauth:grant-type:device_code`, so there's no second list to drift out of sync with
the issuer. `grant_types_supported` is now required, with the JWT bearer and refresh token grants.
A Company whose issuer offers one of these grants to other clients offers it to Personal Agents too.
Direct and Device Sign-In can grant any scope in `scopes_supported`. Only Mediated Sign-In keeps its
own list, `auth.mediated.scopes`.

</Change>

<Change title="Company-defined scopes only" breaking sections="2, 3, 3.1, 4.4, guides#company-scopes">

The protocol no longer defines `poppy:read` and `poppy:write`. Each Company defines its own scopes,
usually the OAuth scopes it already has, and must describe each one, in an OpenAPI description it
lists or in `auth.scopes`. Names starting with `poppy:` stay reserved.

</Change>

<Change title="Prefer delegated sign-in" sections="4.4, 9.5, guides#agent-choosing-sign-in">

Personal Agents should use Direct or Device Sign-In rather than Mediated Sign-In when the Company
offers it and it covers the task. Companies that offer Direct or Device Sign-In should make their
scopes and APIs cover what Users need. Section 9.5 explains what a Company gives up when Personal
Agents sign in with the User's credentials outside the protocol.

</Change>

<Change title="Session Keys replace `session_id`" breaking sections="2, 4, 4.2, 4.3, 4.4, 4.5, 4.6, 4.7, 4.8, guides#agent-dpop, guides#company-session-keys">

Each Session has its own DPoP key, the Session Key, and the key's thumbprint names the Session. The
custom `session_id` parameter is removed from every token request and response, so Poppy's token
requests are standard OAuth requests. A proof from a new key starts a new Session, and a proof from
a known key renews or signs in that Session. Personal Agents use a new key for each Session instead
of one for each User ID. Companies should remember the keys of Sessions they end and reject them
with `invalid_grant`, so an ended Session's key doesn't silently start a new one.

</Change>

<Change title="Browsers join a Session with a signed one-time code" breaking sections="4.3, 5, 9.4, 9.6, 10, guides#both-secrets, guides#agent-browsing, guides#company-browsing">

The Personal Agent's browser no longer posts a signed browser assertion. Any browser could post one,
so a malicious Personal Agent could have a victim's browser join a Session signed in to the
attacker's account. Now the browser loads `web.browser_session_endpoint` with a GET and gets a page
with a form holding a one-time code, and a `SameSite=Strict` cookie that ties the code to that
browser. The Personal Agent signs a DPoP Proof with its Session Key, with the code as its `nonce`,
puts it in the form, and has the browser submit it. The Company checks the cookie, the code, and the
proof, and sets the Session's cookie in its response. The page can't be framed or kept by the page
that opened it. The Personal Agent takes the code only from its own browser, outside its model, and
the guides list the code as a secret. The browser assertion, its `typ`, and `return_to` are removed.
The Session's cookie SHOULD use the `__Host-` prefix, and `SameSite=Strict` is no longer ruled out.
A new section 9.6 explains both attacks the design prevents, and the references add RFC 9111, RFC
6265bis, RFC 9700, and RFC 10027.

</Change>

<Change title="Mediated Sign-In is transitional" sections="3.1, 4.7, 9.5, guides#company-mediated">

Mediated Sign-In is a transitional step, not where the protocol is headed, like OAuth's password
grant. Companies should offer it only until they can add Direct or Device Sign-In, and stop once
those cover the same scopes. The protocol plans to remove it, on a date set when version 1.0 is
published, and after that the community will look for ways to encourage the Companies that still
offer it to move to Direct or Device Sign-In.

</Change>

<Change title="Excluded tasks" sections="3, 3.1, 8, 8.1, 8.2, 9.1, guides#agent-excluded-tasks, guides#company-excluded-tasks">

A Company can list the tasks it chose not to offer through this protocol, so Personal Agents tell
the User right away instead of searching every interface for a way to do them. `excluded_tasks.url`
in `poppy.json` points to a public JSON document of `tasks`, each a short `task` phrase and an
optional `alternative`. An alternative has natural-language `instructions`, `references`, or both. A
reference points to an OpenAPI operation by `operationId`, an MCP tool by name, or a web page, which
can be a link that opens the Company's app. An `openapi` or `mcp` reference MUST name an API listed
in `poppy.json`. Section 8 is now "Tasks a Company doesn't offer", with excluded tasks in 8.1,
alternatives in 8.2, and feedback in 8.3.

</Change>

<Change title="Answering feedback with an alternative" sections="8.3, guides#agent-excluded-tasks, guides#company-excluded-tasks">

A Company can answer a feedback report with HTTP 200 and an alternative (8.2) when the task can be
done after all, instead of 202 with no body. Personal Agents MUST accept either response, and SHOULD
NOT report a task the Company lists as excluded.

</Change>

<Change title="Secrets out of model context" breaking sections="9.2, 10, guides#both-secrets">

Personal Agents must keep Session Tokens, private keys, authorization codes, PKCE code verifiers,
and device codes out of model context, as they already did Account Tokens. Before, these were a
SHOULD. This follows the AI agent identity draft (draft-ietf-wimse-aims §8), which says the model
must not have access to an agent's credentials. Other secrets, such as one-time codes, stay a
SHOULD. The guides list authorization codes and PKCE code verifiers as secrets.

</Change>

### Minor changes {#v0-3-minor}

<Change title="OAuth terms for Poppy names" sections="2">

Section 2 gives the OAuth term for Session Token, Account Token, User ID, sign-in, sign-out, and
signed out, and says why Poppy keeps its own name for each.

</Change>

<Change title="Discovery redirects end at the well-known path" breaking sections="3, 9.3, guides#agent-discovery">

A redirect of the well-known URL can still go to another host, but the Personal Agent uses the
document only when the last URL's path is exactly `/.well-known/poppy.json`, with no query. Before,
a redirect could end at any path, so anyone who could upload a file to a Company's domain could
publish a `poppy.json` there that spoke for the Company, with endpoints on their own host.

</Change>

<Change title="`protected_resources` replaces `poppy_domains`" breaking sections="3, 3.2, 4.6, 9.3, guides#agent-direct-device, guides#company-hosting">

The issuer confirms which domains name it with `protected_resources`, the field RFC 9728 registers in
authorization server metadata, instead of the custom `poppy_domains`. It lists `https://{domain}` for
each domain, exactly in that form with no path or trailing slash, and may list other resources,
such as MCP servers. Personal Agents check that it includes `https://{organization.domain}` by exact
string, ignoring case only in the host, and a device sign-in link's host is checked against the
hosts of its entries.

</Change>

<Change title="`scopes_supported` and `auth.scopes`" breaking sections="3.1, 3.2, 4.4, guides#company-agent-issuer">

A Company lists every scope a Personal Agent can request in `scopes_supported` in its OAuth server
metadata, as RFC 8414 defines, and Personal Agents request only scopes from it. A Company describes
its scopes in the OAuth security scheme of an OpenAPI description it lists, or otherwise in
`auth.scopes`, which replaces `auth.custom_scopes` and has the same form as the `scopes` of an OAuth
2.0 security scheme in OpenAPI. `scopes_supported` may leave out scopes the Company doesn't offer
Personal Agents, and the Company may limit the scopes it grants by client, so an issuer that serves
other clients doesn't need a separate one for Personal Agents. The guides explain when a separate
issuer is still useful.

</Change>

<Change title="Requesting and describing scopes" sections="4.4, guides#agent-choosing-sign-in, guides#company-scope-descriptions, guides#company-consent">

Personal Agents should request only the scopes a task needs, following RFC 9700 §2.3. The guides
add advice on writing scope descriptions a User and a language model can understand, and on consent
pages that present scopes in plain words and show which are new.

</Change>

<Change title="Missing scopes on the website" sections="5, guides#company-scopes">

When a Company's website refuses an action because the Session lacks a scope, it should show a
visible error that names the missing scopes, so the Personal Agent can request them.

</Change>

<Change title="`invalid_session` becomes `invalid_grant`" breaking sections="4.2, 4.8, 4.9">

A Session that has ended, or belongs to a different Personal Agent or User, now gets the standard
`invalid_grant`. `account_mismatch` stays, so the Personal Agent can tell the User they signed in to
a different account.

</Change>

<Change title="Authorization codes bound to the Session Key" breaking sections="3.2, 4.3, 4.5, 4.6, guides#agent-direct-device, guides#company-session-keys">

Companies must support `dpop_jkt`, and Personal Agents must bind the authorization code to the
Session Key with it, or with a proof on a pushed authorization request. A device code is bound to
the key of the first poll.

</Change>

<Change title="Bearer tokens for MCP servers by Token Exchange" breaking sections="3.2, 4.2, 4.3, guides#agent-tokens, guides#company-dpop">

A Personal Agent gets a Bearer token for an MCP server that doesn't support DPoP by exchanging a
DPoP Session Token for it with the token exchange grant (RFC 8693), instead of leaving the proof out
of a token request. Every other token request carries a proof. A Company that lists such an MCP
server must support the grant. A request for the wrong token type gets `invalid_target`.

</Change>

<Change title="The OAuth specifications Poppy builds on" sections="4, 4.2, 10">

Section 4 lists the OAuth specifications the protocol builds on, instead of calling it standard
OAuth: RFC 6749, RFC 7523, RFC 7636, RFC 8628, RFC 9449, RFC 8707, RFC 7009, and RFC 9700. Section
4.2 cites RFC 7523 §2.1 for the grant that starts a Session, and notes that the Personal Agent
issues the assertion itself, as in draft-ietf-wimse-aims §10.4.2. The references add RFC 8693,
which 4.3 already used, and draft-ietf-wimse-aims.

</Change>

<Change title="User IDs as pairwise identifiers" sections="4.2, 10">

Section 4.2 relates User IDs to OpenID Connect pairwise subject identifiers, which the Personal Agent
assigns for each pair of User and Company. The rules for User IDs don't change.

</Change>

<Change title="`signed_in` removed" breaking sections="4.2, 4.3, 4.4, 4.7, guides#agent-choosing-sign-in">

Token responses no longer have `signed_in`. The grant says whether a token is signed in: the JWT
bearer grant always returns a signed-out Session Token, and a sign-in or an Account Token always
returns a signed-in one. `scope` follows RFC 6749: a signed-out token's response leaves it out,
since an empty `scope` isn't valid OAuth, and a signed-in one includes it unless the Company granted
exactly the scopes requested. A sign-in where the User approves no scopes ends as a decline.

</Change>

<Change title="Device Sign-In follows RFC 10027" breaking sections="4.6, guides#agent-direct-device, guides#company-device">

Device Sign-In is a cross-device flow, which is easier to use for phishing than Direct Sign-In.
Companies that offer it and Personal Agents that use it must follow the best practices in RFC 10027
(BCP 247) §2: a Company assesses the risk and chooses mitigations, and a Personal Agent uses Direct
Sign-In when it can, as the RFC's protocol selection guidance says. The guides suggest sending the
authorization URL to the User's phone when a Personal Agent can't receive the redirect on the
User's device, and list mitigations for Companies.

</Change>

<Change title="`sign_in_required` becomes `insufficient_scope`" breaking sections="4.4, 4.9, 6, 7.11, Operations 3.2, guides#company-conversations">

A request that needs the User's account and has a signed-out token gets `insufficient_scope`, the
RFC 6750 error, instead of the custom `sign_in_required`. A signed-out token has no scopes, so the
error fits, and like any `insufficient_scope` it names the scopes the request needs in `scope`.
The Personal Agent uses an Account Token that covers them, or signs in. The `authorization`
conversation event and Operations use the same error.

</Change>

<Change title="Sign-out invalidates Session Tokens" sections="4.9">

When the Personal Agent revokes an Account Token, the Company should also invalidate the Session
Tokens issued under the same sign-in, as RFC 7009 §2.1 describes. Checking on each request whether
the Session is still signed in, and short Session Token lifetimes, become the fallbacks.

</Change>

<Change title="What Poppy adds to OAuth" sections="4, 4.10">

A new section 4.10 lists what a Company's authorization server needs beyond standard OAuth, such as
Sessions named by DPoP keys, one account per Session, and described scopes, and what the protocol
adds outside OAuth. It adds no requirements.

</Change>

## Version 0.2 {#v0-2}

Published October 24, 2026. It's frozen at [/docs/0.2/spec](/docs/0.2/spec). Major changes are
design decisions. Minor changes fill gaps, make the text consistent, or follow an RFC. A change
tagged "Breaking" can require an implementation that followed the 0.1 text to change, whether it's
major or minor.

### Major changes {#v0-2-major}

<Change title="Which domain `poppy.json` speaks for" breaking sections="3, 3.1, 3.2" issue="5">

`organization.domain` is the host that serves the document after any redirects, not the host the
Personal Agent requested. Domains are compared ignoring case only, so a leading `www.` is no longer
ignored, and the `poppy_domains` check also ignores case. A Company that uses a provider has the
provider serve the document on the Company's own domain.

</Change>

<Change title="One issuer per Company" breaking sections="3.2, 4.2, 9.4" issue="3">

An issuer represents exactly one Company. A provider that hosts several Companies gives each its own
issuer, even on shared servers, so they don't share User IDs or Account Tokens. The spec also says
where the metadata is for an issuer with a path, as RFC 8414 defines.

</Change>

<Change title="Assertion audience" breaking sections="4.1, 4.2, 9.4" issue="2">

In 0.1, a client assertion's `aud` wasn't specified, and a Session assertion's was the Company's
token endpoint. Both are now the Company's `auth.issuer`, and Companies reject any other `aud`.

</Change>

<Change title="User IDs for anonymous browsing" sections="4.2" issue="11">

A Personal Agent may give a User a new User ID for each anonymous browsing session, like a private
browser window, and never signs in with it. Personal Agents must keep the mapping of each User's IDs
across Companies confidential: no publishing it and no sharing it with third parties, other than
service providers that process it for them.

</Change>

<Change title="A DPoP key per User ID" breaking sections="4.3">

Personal Agents use a different DPoP key pair for each User ID, so Companies can't link Users by
their keys.

</Change>

<Change title="DPoP at MCP servers" breaking sections="4.3, 6" issue="6">

An MCP server supports DPoP by listing `dpop_signing_alg_values_supported`, with `ES256`, in its
protected resource metadata. The Company chooses the token type by the `resource` of the token
request: a DPoP Session Token for such a server, never a Bearer one for a Personal Agent, and a
Bearer token for any other MCP server, even if the request has a proof. Every token request for an
MCP server, including one that starts a Session, includes `resource`. A Bearer token works only at
the MCP server whose `url` is its `resource`, not at other paths on the same host. A server with
DPoP still accepts Bearer tokens from MCP clients that don't implement this protocol, and rejects a
DPoP token sent as a Bearer token. An MCP server's 401 has a challenge for each scheme it accepts,
each with `resource_metadata`. New MCP servers should support DPoP.

</Change>

<Change title="A Session stays tied to its account" breaking sections="4.4, 4.8, 4.9" issue="8">

Once a Session has been signed in to an account, it can only be signed in to that account again,
even after sign-out. This applies to every sign-in type, and to using an Account Token with a
signed-out Session.

</Change>

<Change title="Device sign-in links" breaking sections="4.6">

Personal Agents show `verification_uri` only if its host is the Company's issuer host or one of its
`poppy_domains`, and show the Company's name and domain with it, so a Company can't pass off another
Company's sign-in page as its own.

</Change>

<Change title="Mediated Sign-In credentials" breaking sections="4.7" issue="5">

After a sign-in ends, Personal Agents MUST discard the credentials or keep them only in a credential
store the User chose, such as a password manager. They MUST NOT keep them anywhere else, including
model context and logs. After the User or the Company revokes their access, they SHOULD NOT sign in
again with stored credentials unless the User asks.

</Change>

<Change title="After sign-out" breaking sections="4.9, 6, 7.11">

Section 4.9 gathers the rules for a Session that continues signed out after the User signs out or
disconnects the Personal Agent. What doesn't need the account carries on. Anything that used it,
such as a conversation or an operation, stays as it is, and a signed-out token gets
`sign_in_required` on it. A conversation stays open, so the User can sign in again and continue it.
The Personal Agent SHOULD NOT sign in to that account again unless the User asks, even when a
request gets `sign_in_required`.

</Change>

<Change title="Feedback" sections="3.1, 8" issue="9">

A new section 8 lets a Company list a `feedback.endpoint` in `poppy.json`. With a Session Token,
Personal Agents can report a User's task that the Company offers no way to do through this protocol.
A report has a `kind`, which is `missing` for now, the `task`, and a `description` without
identifiers, and isn't for errors.

</Change>

<Change title="Security considerations" breaking sections="9, 9.1" issue="4">

A new section 9 covers content from Companies and prompt injection, secrets and the model, what a
domain vouches for, and why assertions name the issuer. It adds requirements for Personal Agents:
they MUST treat content from a Company as data, not instructions, and MUST NOT act at one Company,
or send it information, because another Company's content asked. References move to section 10.

</Change>

### Minor changes {#v0-2-minor}

<Change title="HTTPS everywhere" breaking sections="3">

Every URL the protocol defines or exchanges is an HTTPS URL, including API and MCP URLs, metadata
endpoints, and extension endpoints, which 0.1 didn't cover. Personal Agents don't use other URLs
from a Company, and Companies reject them from a Personal Agent. Website pages a Personal Agent
browses aren't covered.

</Change>

<Change title="Redirects and addresses" breaking sections="3">

Outside discovery, a Personal Agent doesn't send a token, DPoP Proof, assertion, or credentials to
the URL a protocol endpoint redirects to. Neither side connects to loopback, private, or link-local
addresses for URLs the other gave it, unless configured to.

</Change>

<Change title="Which Company a document speaks for" sections="3, 3.2, 9.3">

Section 3 now explains in one place how `poppy.json` and the issuer's metadata confirm each other,
and 3.2 lists `issuer` and `poppy_domains` among the metadata fields. The issuer is compared exactly
and domains ignoring case. The redirect example now matches the example document. The rules
themselves don't change.

</Change>

<Change title="Versions before 1.0" breaking sections="3.1">

Each 0.x version can break the one before, so a Personal Agent uses only a `poppy.json` whose
`major.minor` version it supports. 0.1 promised that newer minor versions wouldn't break older
Personal Agents, which 0.2 doesn't keep. That promise now starts at 1.0.

</Change>

<Change title="One `auth` per issuer" breaking sections="3.2">

Documents on several domains that name the same issuer have the same `auth`. Other fields can differ
by domain.

</Change>

<Change title="DPoP algorithms" breaking sections="3.2" issue="12">

Companies accept DPoP Proofs signed with `ES256`. They may list the algorithms they accept in
`dpop_signing_alg_values_supported` in their OAuth metadata, and the list then includes `ES256`. A
Company whose issuer serves other OAuth clients can leave the field out, since it tells them the
issuer supports DPoP. Personal Agents sign with `ES256` or an algorithm from the list.

</Change>

<Change title="`extension_required` responses" breaking sections="3.3, 4.2, 6">

At the token endpoint and at endpoints this protocol or an extension defines, the error is a JSON
body. At APIs, it goes in the `WWW-Authenticate` header. It's listed in the token endpoint and API
error tables. An MCP server returns it only to refuse the Personal Agent entirely, never for a
single tool.

</Change>

<Change title="Assertion lifetimes and replay" breaking sections="4.1, 4.2">

A Session assertion's `exp` is at most five minutes after `iat`, and Companies reject a reused `jti`
from the same `client_id` until it expires. Client assertions follow the same rules, and `aud` is
compared character for character.

</Change>

<Change title="DPoP Proof checks" breaking sections="4.3">

Companies MUST validate every proof as RFC 9449 §4.3 describes. That adds checks that the request
has exactly one `DPoP` header, `typ` is `dpop+jwt`, `alg` is an asymmetric algorithm the Company
accepts and never `none`, and `jwk` holds no private key. In 0.1, every endpoint had to reject a
reused `jti`. Now only the token endpoint must, and APIs and conversation endpoints may. A Company
can judge the acceptance window by when it issued the proof's `nonce`, not only by `iat`. Companies
don't need to support `dpop_jkt`. Where the spec is silent, RFC 9449 applies.

</Change>

<Change title="DPoP errors at APIs and conversations" breaking sections="4.3, 6">

`invalid_dpop_proof` and `use_dpop_nonce` come with HTTP 401 and the `WWW-Authenticate: DPoP`
header. At the token endpoint they're OAuth errors with HTTP 400.

</Change>

<Change title="Which requests carry a DPoP Proof" sections="4.3">

Every request to the token endpoint and every request with a Session Token carries a proof, except a
request for a Bearer token for an MCP server. Requests that carry neither, such as revocation and
device authorization, don't need one.

</Change>

<Change title="`rate_limited` body" sections="4.3">

At the token endpoint and at endpoints this protocol or an extension defines, such as conversations
and Mediated Sign-In, the body is `{"error": "rate_limited"}`. APIs and the website keep their own
bodies.

</Change>

<Change title="Mediated Sign-In responses" breaking sections="4.7">

Every status comes with HTTP 200, and submitting a code to a `failed` or `expired` sign-in returns
the same status again. Problems with the request are errors with a JSON body: `invalid_scope` and
`account_mismatch` (400), and `sign_in_not_found` (404) for a sign-in that is unknown or that
another Session started.

</Change>

<Change title="Mediated Sign-In for the right Company" breaking sections="4.7">

Personal Agents choose stored credentials by the Company's `auth.issuer`, not by field labels or the
endpoint, and show the Company's name and domain when asking for credentials or a code.

</Change>

<Change title="Work after a token expires" sections="4.9" issue="15">

A Session Token expiring isn't a sign-out, and work the Company accepted with a valid token can
continue. When access is revoked, the Company may stop work in progress that uses the account, or
let it finish.

</Change>

<Change title="Sessions from plain MCP clients" sections="6">

A Session started by an MCP client that doesn't implement this protocol has no User ID, can't
continue signed out, and ends when its sign-in does.

</Change>

<Change title="Conversation query parameters" sections="7.3, 7.5">

`cursor` and `wait` are query parameters, as the 0.1 examples showed, on reads and on the `POST`
requests that send a message or hand off. `wait` is a whole number of seconds.

</Change>

<Change title="Messages" breaking sections="7.4, 7.5">

`role` is listed as a message field, set by the Company. A `message` event holds the message as it
was sent, and every accepted message is recorded, including one with only `context`.

</Change>

<Change title="Long polling" sections="7.5">

A Company that caps `wait` holds the request for its cap instead of rejecting it.

</Change>

<Change title="Read fields" breaking sections="7.5" issue="13">

Every successful read includes `conversation_id` and `events`, as the examples showed, along with
`cursor`, `has_more`, `status`, and `responder`. `events` is empty when there are none.

</Change>

<Change title="Streaming" sections="7.6">

When a request has both `Last-Event-ID` and `cursor`, `Last-Event-ID` wins.

</Change>

<Change title="Repeated requests" sections="7.9, 7.12">

Handing off a conversation that is already queued or with a person, or closing one that is already
closed, returns the current state and changes nothing.

</Change>

<Change title="`user_requested`" sections="7.10">

The event doesn't change `status` or `responder`.

</Change>

<Change title="Conversation errors" sections="7.13">

Conversations add `invalid_request` (400) and `rate_limited` (429).

</Change>

<Change title="Browser assertion audience" sections="9.4">

Section 9.4 now says that client and Session assertions name the issuer, and that a browser
assertion names the browser session endpoint and has its own `typ`.

</Change>

<Change title="`extension_required` in conversations and Operations" sections="7.13, Operations 2, Operations 9">

The conversation error table lists `extension_required`. An MCP tool that needs the Operations
extension returns an ordinary tool error, since an MCP server can't refuse a single tool call with
`extension_required`. The Operations error table lists `rate_limited` and no longer lists
`extension_required`.

</Change>

<Change title="Operations after sign-out" breaking sections="Operations 3.2">

An operation proposed in a signed-in Session can be used only by a Session that is signed in to the
same account at the time of the request, including the original one. A signed-out Session of the
same Personal Agent and User gets `sign_in_required`.

</Change>

<Change title="Operations" sections="Operations 5.1" issue="4">

Personal Agents should show the User the values in an operation's `terms` next to its `summary`, or
check that they agree, before asking for approval.

</Change>

<Change title="Examples" sections="7.3, Operations 4.3">

The request that waits for a reply is shown in full, the API write examples include an
`Idempotency-Key`, the example DPoP Proof's `jti` has 128 random bits, and the Operations
conversation example has its own event ID.

</Change>

### Guides {#v0-2-guides}

Advice that goes with the spec. Guides aren't requirements.

<Change title="Signing, replay caches, and Mediated Sign-In" sections="Guides" issue="5">

Sign DPoP Proofs with ES256, which every company accepts. A company's token endpoint keeps a replay
cache shared by every server, and its APIs may keep one too. A client or Session assertion's `aud`
is the company's `auth.issuer`. Personal agents keep Mediated Sign-In credentials only in a
credential store the user chose, and don't sign in with them again after the user disconnects.
Companies ask for a one-time code on a personal agent's first mediated sign-in after the user
disconnected it.

</Change>

<Change title="Key refetches, rate limits, and running work" sections="guides#both-key-rotation, guides#both-rate-limits, guides#company-lifetimes" issue="15">

Companies refetch a personal agent's keys at most once per interval, counting failures, and charge
per-agent rate limits only after the signature checks pass. Accepted work isn't stopped because a
session token expired, and work that can take consequential actions stops right away when access is
revoked.

</Change>

<Change title="Hosting several companies" sections="guides#company-hosting, guides#agent-user-ids" issue="3">

A new section for providers that host several companies, with an example of which storefronts share
an issuer, metadata for an issuer with a path, and keeping each company's tokens and records apart
on shared servers. Personal agents key user IDs and account tokens by the full `auth.issuer`.

</Change>

<Change title="Conversations after sign-out" sections="guides#company-conversations">

Companies can leave conversations that used the account open after sign-out, answering signed-out
tokens with `sign_in_required`, instead of closing them.

</Change>

<Change title="User ID privacy" sections="guides#agent-user-ids" issue="11">

Personal agents tell users that companies recognize them across signed-out visits and that signing
in links those visits to their account. A new list covers anonymous browsing: a new user ID and DPoP
key for each session, discarded when it ends.

</Change>

<Change title="Finding a company" sections="guides#agent-discovery">

When the company a personal agent reaches is on a different domain from the one the user asked for,
it tells the user which company it's dealing with before signing in or acting for them.

</Change>

<Change title="Matching the spec" sections="Guides">

Personal agents sign assertions and proofs with ES256, and don't send a token or proof to the URL a
protocol endpoint redirects to. Mediated Sign-In credentials are discarded or stored when a sign-in
ends. Without a browser session endpoint, personal agents browse only as signed-out visitors. The
token endpoint's replay rule and `iss` in Direct Sign-In redirects cite the spec without overstating
it.

</Change>
